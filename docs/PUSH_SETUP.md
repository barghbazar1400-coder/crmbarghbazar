# اعلان‌های CRM — راهنمای استقرار و پذیرش

دو لایه مستقل وجود دارد:
1. **اعلان داخل CRM:** بدون Composer؛ زنگ بالای صفحه، فهرست خوانده‌نشده، پیام جدید، واگذاری و انتقال وظیفه، تغییر وضعیت توسط مدیر، تکمیل وظیفه و راهنمایی مدیر. با خواندن پیام داخلی، اعلان مربوط نیز خوانده می‌شود. اطلاعیه مدیریت برای همه، یک کارمند یا اعضای یک واحد منتشر می‌شود.
2. **Web Push واقعی:** تنها پس از فعال‌سازی اختیاری روی سرور و صدور مجوز مرورگر با دکمه توسط هر کارمند؛ حتی با بسته بودن تب CRM قابلیت نمایش اعلان عمومی را دارد. هیچ متن خصوصی در Push نشان داده نمی‌شود و باز کردن جزئیات همچنان به ورود و سطح دسترسی نیاز دارد.

## پیش‌نیازها

- HTTPS معتبر در دامنه CRM و مرورگر پشتیبان Service Worker، Push API و Notifications.
- PHP 8.2+ و افزونه‌های curl، mbstring، openssl با EC.
- Composer برای نصب minishlink/web-push نسخه 11.0.0 در پوشه قالب فعال CRM.
- دسترسی خروجی HTTPS سرور به Push service مرورگرها.
- WP-Cron فعال یا cron سیستمی معادل برای همین سایت. اجرای زمان‌بند جدید روی سرور در این تغییر انجام نشده است.

پس از بکاپ دیتابیس، فرمان انتشار دستی:

~~~bash
bash "$HOME/.crmbarghbazar-deploy/deploy.sh"
~~~

در پوشه قالب فعال CRM روی هاست:

~~~bash
php -v
php -m | grep -Ei 'curl|mbstring|openssl'
composer install --no-dev --prefer-dist --optimize-autoloader --no-interaction
~~~

برای یافتن پوشه قالب و نسخه واقعی PHP از تنظیمات هاست یا WP-CLI استفاده شود؛ مسیر حدس زده نشود. پوشه vendor از Git کنار گذاشته شده و بسته به اسکریپت deploy ممکن است پس از هر انتشار نصب مجدد لازم باشد.

بعد از نصب Composer، مدیر کل وارد صفحه «اعلان‌ها و اطلاعیه‌ها» شود و «ایجاد کلیدهای پوش سرور» را فقط یک بار بزند. کلید خصوصی VAPID به‌صورت non-autoload در دیتابیس، نه مخزن Git، ذخیره می‌شود. **کلید را بی‌دلیل عوض نکنید** چون اشتراک‌های فعلی مرورگرها را نامعتبر می‌کند.

هر کارمند روی «فعال‌سازی پوش روی این سیستم» کلیک می‌کند و اجازه اعلان را به مرورگر می‌دهد. در سیستم مشترک بهتر است قبل از تغییر کاربر، پوش غیرفعال شود. کارمند در هر زمان می‌تواند پوش مرورگر خودش را غیرفعال کند.

## معماری و حدود عملکرد

- جداول افزایشی crmb_notifications و crmb_push_devices با پیشوند واقعی وردپرس؛ جداول پیام و وظیفه فعلی دست‌نخورده‌اند.
- فایل inc/notifications.php برای اعلان‌های scoped، اطلاعیه مدیر و خواندن/شمارنده.
- فایل inc/notifications-push.php برای VAPID، صف ارسال، اعتبارسنجی سخت‌گیرانه مقصد HTTPS، حذف endpoint منقضی، و مدیریت دستگاه.
- Service Worker از admin-ajax.php?action=crmb_push_sw با هدر Service-Worker-Allowed: / و MIME application/javascript ارائه می‌شود، بدون کش و بدون intercept کردن درخواست‌ها.
- فایل assets/js/crmb-notices.js در صفحه اصلی inline اجرا می‌شود؛ در تب باز شمارنده هر ۴۵ ثانیه polling می‌شود.
- صف در رویداد کوتاه‌مدت WP-Cron و رویداد پشتیبان پنج‌دقیقه‌ای بررسی می‌شود. تحویل فوری تضمین‌شده نیست، به‌ویژه وقتی WP-Cron غیرفعال باشد یا مرورگر/OS Push را به تأخیر بیندازد.
- متن خصوصی پیام یا اطلاعیه به سرویس Web Push ارسال نمی‌شود.

## آزمون‌ها

~~~bash
php -l inc/notifications.php
php -l inc/notifications-push.php
php -l inc/work.php
php -l inc/progress.php
php -l inc/task-rich-notes.php
php -l page-main.php
php -l template-parts/notifications.php
php tests/notifications.php
php tests/progress.php
~~~

آزمون مستقل notifications.php به PDO SQLite نیاز دارد و Push provider واقعی را فراخوانی نمی‌کند.

معیار پذیرش: پیام B فقط در اعلان‌های B دیده شود و با «خواندم» پاک شود؛ تغییر وظیفه و راهنمایی مدیر اعلان صحیح ایجاد کند؛ اطلاعیه عمومی/کارمند/واحد فقط برای مخاطبان ثبت شود؛ POST غیرمجاز یا nonce نامعتبر رد شود؛ مرورگر با رضایت پوش بگیرد و بتواند غیرفعالش کند؛ با تب بسته و WP-Cron فعال اعلان عمومی برسد؛ درخواست Service Worker در Network، پاسخ 200 و هدرهای صحیح داشته باشد؛ endpoint خصوصی یا میزبان نامجاز رد شود.

**وضعیت:** کدنویسی مخزن به معنای استقرار و آزمون واقعی سایت نیست. تنظیمات و کلیدهای پوش باید فقط روی هاست واقعی ایجاد و بررسی شوند.
